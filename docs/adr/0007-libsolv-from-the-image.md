# The host tier resolves with the image's own libsolv

The host tier has to answer what dnf answers: given the image's installed
set and Fedora's repos, which RPMs does a request add? nx links the libsolv
the image already carries (dnf5 and rpm-ostree use it) through bindings
generated by bindgen and checked in, in one crate, `nx-solv`.

- **libsolv, not a solver of our own.** RPM dependency rules (rich deps,
  file provides, obsoletes, arch policy, multiversion) are the long tail, and
  libsolv is what Fedora's own tools resolve with. Matching dnf's answers is
  the point.
- **The image's copy, linked dynamically.** It is already in `/usr`, its
  `repo_add_rpmdb` reads the image's rpmdb with the same librpm the image
  wrote it with, and its `repo_add_rpmmd` and `solv_xfopen` read zstd
  metadata. nx builds per Fedora release anyway (ADR-0006 amends ADR-0005).
- **Bindings checked in, not generated at build time.** `bindgen` runs from
  `crates/nx-solv/generate.sh` in the dev container (`dev/Containerfile`)
  and writes `src/sys.rs`, allowlisted to the functions nx calls. Building
  nx then needs only `libsolv-devel`, not clang. Regenerate when the libsolv
  soname changes.
- **`unsafe` lives in `nx-solv` alone.** The workspace denies `unsafe_code`;
  `nx-solv` allows it and exposes a safe `Pool` API. Nothing else in nx
  calls libsolv.

## Considered

- **A pure-Rust solver (resolvo, pubgrub).** Neither speaks RPM's rule set,
  and nx would own every disagreement with dnf.
- **Shelling out to dnf5** (`dnf5 --installroot … install --assumeno`).
  It works without root only partly, prints for humans, and costs a second
  or more per call before resolving anything.
- **The `libsolv-sys` crate on crates.io.** It vendors and builds its own
  libsolv, which is the copy nx explicitly wants not to carry.
